2. HOW DATA BINDING WORKS (STEP-BY-STEP)
================================================================================

Let's trace what happens when you type in the "Project Name" textbox:

STEP 1: XAML BINDING SETUP (at startup)
----------------------------------------
XAML File: GeneralSettingsView.xaml

    <TextBox Text="{Binding ProjectName, Mode=TwoWay}"/>
             ↑      ↑       ↑               ↑
             │      │       │               └─ Data flows both ways
             │      │       └───────────────── Property name in ViewModel
             │      └───────────────────────── Binding expression
             └──────────────────────────────── TextBox property to bind

When this XAML loads, WPF:
1. Looks at the View's DataContext (which is GeneralSettingsViewModel)
2. Searches for a property named "ProjectName"
3. Creates a binding between TextBox.Text and ViewModel.ProjectName
4. Subscribes to PropertyChanged events from the ViewModel

STEP 2: INITIAL VALUE DISPLAY (View ← ViewModel)
-------------------------------------------------
At startup, the ViewModel might have:

    public string ProjectName { get; set; } = "My ML Project";

WPF automatically:
1. Reads the ProjectName value ("My ML Project")
2. Sets TextBox.Text = "My ML Project"
3. Displays it in the UI

YOU SEE: TextBox shows "My ML Project"

STEP 3: USER TYPES IN TEXTBOX (View → ViewModel)
-------------------------------------------------
User types: "Customer Churn Prediction"

What happens (microsecond by microsecond):

1. User presses 'C' key
   └─ TextBox.Text changes to "C"

2. WPF binding system detects change (UpdateSourceTrigger=PropertyChanged)
   └─ Immediately triggers update

3. Binding calls ViewModel's ProjectName setter:

   set
   {
       _projectName = "C";  // Stores new value
       OnPropertyChanged(nameof(ProjectName));  // Notifies subscribers
   }

4. User continues typing...
   Each keystroke repeats steps 1-3

5. Final value: "Customer Churn Prediction"

STEP 4: VIEWMODEL NOTIFIES UI (ViewModel → View)
-------------------------------------------------
If ViewModel changes the property programmatically:

    ProjectName = "Updated by Code";

The setter runs:

    set
    {
        _projectName = "Updated by Code";
        OnPropertyChanged(nameof(ProjectName));  ← CRITICAL!
                          ↓
                PropertyChanged event fired
                          ↓
            WPF binding system listens
                          ↓
                Updates TextBox.Text
                          ↓
            UI refreshes automatically
    }

YOU SEE: TextBox text changes to "Updated by Code"

5. PROPERTYCHANGED MECHANISM EXPLAINED
================================================================================

The magic behind automatic UI updates is INotifyPropertyChanged.

BASE IMPLEMENTATION (BaseViewModel.cs):

    public class BaseViewModel : INotifyPropertyChanged
    {
        public event PropertyChangedEventHandler PropertyChanged;

        protected void OnPropertyChanged(string propertyName)
        {
            PropertyChanged?.Invoke(this,
                new PropertyChangedEventArgs(propertyName));
        }

        protected bool SetProperty<T>(ref T field,
                                     T value,
                                     [CallerMemberName] string propertyName = "")
        {
            if (EqualityComparer<T>.Default.Equals(field, value))
                return false;  // No change, don't notify

            field = value;  // Update backing field
            OnPropertyChanged(propertyName);  // Notify UI
            return true;
        }
    }

USAGE IN CHILD VIEWMODEL:

    public class GeneralSettingsViewModel : BaseViewModel
    {
        private string _projectName;

        public string ProjectName
        {
            get => _projectName;
            set => SetProperty(ref _projectName, value);
                   ↑
                   This does:
                   1. Check if value changed
                   2. Update _projectName
                   3. Fire PropertyChanged event
                   4. WPF bindings update UI
        }
    }

WHAT HAPPENS UNDER THE HOOD:

1. Property changes:
   ProjectName = "New Value";

2. Setter calls SetProperty:
   SetProperty(ref _projectName, "New Value", "ProjectName");

3. SetProperty checks if changed:
   if (_projectName == "New Value") return false;  // No change
   _projectName = "New Value";  // Update

4. SetProperty fires event:
   PropertyChanged?.Invoke(this,
       new PropertyChangedEventArgs("ProjectName"));
       ↑
       This says: "Hey, ProjectName property changed!"

5. WPF binding system hears event:
   if (e.PropertyName == "ProjectName")
   {
       UpdateBinding();  // Refresh UI element
   }

6. UI element updates:
   TextBox.Text = viewModel.ProjectName;  // "New Value"

VISUAL FLOW:

    ViewModel                          WPF Binding System
    ─────────                          ──────────────────

    ProjectName = "X"
        ↓
    SetProperty(...)
        ↓
    _projectName = "X"
        ↓
    PropertyChanged?.Invoke(...)
        ↓
        ────────────────────────────→ Event received
                                          ↓
                                      Check property name
                                          ↓
                                      Find bound controls
                                          ↓
                                      Update TextBox.Text
                                          ↓
                                      User sees "X"

MULTIPLE NOTIFICATIONS:

Sometimes changing one property affects others:

    public bool UseAutoML
    {
        get => _useAutoML;
        set
        {
            if (SetProperty(ref _useAutoML, value))
            {
                // This property changed

                OnPropertyChanged(nameof(UseTraditionalTraining));
                // Notify dependent property 1

                OnPropertyChanged(nameof(TrainingModeDescription));
                // Notify dependent property 2
            }
        }
    }

WPF receives THREE PropertyChanged events:
1. "UseAutoML" → Updates AutoML radio button
2. "UseTraditionalTraining" → Updates Traditional radio button
3. "TrainingModeDescription" → Updates description text

ALL THREE UI ELEMENTS UPDATE FROM ONE USER ACTION!

RELAYCOMMAND IMPLEMENTATION:

    public class RelayCommand : ICommand
    {
        private readonly Action<object> _execute;
        private readonly Func<object, bool> _canExecute;

        public RelayCommand(Action<object> execute,
                           Func<object, bool> canExecute = null)
        {
            _execute = execute;
            _canExecute = canExecute;
        }

        public bool CanExecute(object parameter)
        {
            return _canExecute == null || _canExecute(parameter);
        }

        public void Execute(object parameter)
        {
            _execute(parameter);
        }

        public event EventHandler CanExecuteChanged
        {
            add { CommandManager.RequerySuggested += value; }
            remove { CommandManager.RequerySuggested -= value; }
        }
    }

CANEXECUTE REFRESH:

WPF automatically re-evaluates CanExecute when:
- User interacts with UI
- Focus changes
- Property values change

You can force refresh:
    CommandManager.InvalidateRequerySuggested();

EXAMPLE WITH PARAMETER:

XAML:
    <Button Content="Delete"
            Command="{Binding DeleteCommand}"
            CommandParameter="{Binding SelectedItem}"/>

ViewModel:
    DeleteCommand = new RelayCommand(
        execute: item => DeleteItem((DataItem)item),
        canExecute: item => item != null

8. TWO-WAY BINDING IN ACTION

Two-way binding means data flows BOTH directions:
- View → ViewModel (user input)
- ViewModel → View (programmatic changes)

                            Mode=TwoWay,
                            UpdateSourceTrigger=PropertyChanged,
                            Converter={StaticResource StringToIntConverter}}"/>

ViewModel (TrainingParametersViewModel.cs):

    private int _maxExperimentTimeInSeconds = 30;

    public int MaxExperimentTimeInSeconds
    {
        get => _maxExperimentTimeInSeconds;
        set => SetProperty(ref _maxExperimentTimeInSeconds,
                          Math.Max(1, Math.Min(3600, value)));
                          ↑
                          Validates: must be between 1 and 3600
    }

UPDATEDSOURCETRIGGER OPTIONS:

1. PropertyChanged (our choice):
   - Updates on every keystroke
   - Immediate validation
   - Real-time feedback

2. LostFocus:
   - Updates when user tabs away
   - Less frequent updates
   - Better performance for complex validation

3. Explicit:
   - Only updates when you call UpdateSource()
   - Full manual control

9. COLLECTION BINDING FLOW
================================================================================

Collections need special handling for UI updates.

WRONG WAY (List<T>):

    public List<string> Items { get; set; } = new List<string>();

    public void AddItem(string item)
    {
        Items.Add(item);
        // UI DOES NOT UPDATE! ❌
    }

Problem: List<T> doesn't notify UI of changes

RIGHT WAY (ObservableCollection<T>):

    public ObservableCollection<string> Items { get; } =
        new ObservableCollection<string>();

    public void AddItem(string item)
    {
        Items.Add(item);
        // UI UPDATES AUTOMATICALLY! ✓
    }

EXAMPLE: PARAMETER LIST IN TRAINING PARAMETERS

XAML (TrainingParametersView.xaml):

    <ListView ItemsSource="{Binding Parameters}">
        <ListView.View>
            <GridView>
                <GridViewColumn Header="Name"
                               DisplayMemberBinding="{Binding Name}"/>
                <GridViewColumn Header="Value"
                               DisplayMemberBinding="{Binding ValueString}"/>
            </GridView>
        </ListView.View>
    </ListView>

    <Button Content="Add Parameter"
            Command="{Binding AddParameterCommand}"/>

ViewModel (TrainingParametersViewModel.cs):

    public ObservableCollection<ParameterItem> Parameters { get; } =
        new ObservableCollection<ParameterItem>();

    public ICommand AddParameterCommand { get; private set; }

    private void ExecuteAddParameter(object param)
    {
        // Show dialog to get parameter details
        var dialog = new ParameterDialog();
        if (dialog.ShowDialog() == true)
        {
            var newParam = new ParameterItem
            {
                Name = dialog.ParameterName,
                ValueString = dialog.ParameterValue
            };

            Parameters.Add(newParam);
            ↑
            ObservableCollection fires CollectionChanged event
            ↓
            WPF binding system listens
            ↓
            ListView adds new row automatically
            ↓
            User sees new parameter in list
        }
    }

OBSERVABLECOLLECTION EVENTS:

When you add/remove items:

    Parameters.Add(item);
        ↓
    CollectionChanged event fired:
    {
        Action: Add,
        NewItems: [item],
        NewStartingIndex: 5
    }
        ↓
    ListView.ItemsSource binding hears event
        ↓
    ListView creates new row at index 5
        ↓
    DataTemplate renders item

When you remove:

    Parameters.RemoveAt(3);
        ↓
    CollectionChanged event fired:
    {
        Action: Remove,
        OldItems: [removed item],
        OldStartingIndex: 3
    }
        ↓
    ListView removes row at index 3

When you clear:

    Parameters.Clear();
        ↓
    CollectionChanged event: Action = Reset
        ↓
    ListView clears all rows

NESTED OBJECT UPDATES:

ObservableCollection notifies when collection changes (add/remove),
but NOT when individual items change.

For item updates to reflect:

    public class ParameterItem : INotifyPropertyChanged
    {
        private string _valueString;

        public string ValueString
        {
            get => _valueString;
            set
            {
                _valueString = value;
                OnPropertyChanged(nameof(ValueString));
                ↑
                This updates the ListView cell!
            }
        }
    }

COMPLETE FLOW:

User edits parameter value in ListView:

    ListView cell TextBox loses focus
        ↓
    Binding updates: ParameterItem.ValueString = "new value"
        ↓
    ParameterItem raises PropertyChanged
        ↓
    ListView cell TextBlock updates
        ↓
    User sees changed value

Later, user clicks "Add Parameter":

    AddParameterCommand executes
        ↓
    Parameters.Add(newParam)
        ↓
    CollectionChanged fires
        ↓
    ListView adds new row
        ↓
    User sees new parameter

BINDING TO NESTED COLLECTIONS:

XAML:
    <ComboBox ItemsSource="{Binding AvailableAlgorithms}"
              SelectedItem="{Binding SelectedAlgorithm}"/>

    <ListView ItemsSource="{Binding Parameters}">
        <!-- Parameters for selected algorithm -->
    </ListView>

ViewModel:
    private string _selectedAlgorithm;
    public string SelectedAlgorithm
    {
        get => _selectedAlgorithm;
        set
        {

            {
                LoadAlgorithmParameters();
                ↓

            }
        }
    }

    private void LoadAlgorithmParameters()
    {
        Parameters.Clear();  // Clear old parameters

        switch (SelectedAlgorithm)
        {
            case "fasttree":
                Parameters.Add(new ParameterItem("NumberOfTrees", "100"));
                Parameters.Add(new ParameterItem("MinDocuments", "10"));
                break;

            case "lightgbm":
                Parameters.Add(new ParameterItem("NumberOfLeaves", "31"));
                Parameters.Add(new ParameterItem("LearningRate", "0.1"));
                break;
        }
        ↓
        Each Add() fires CollectionChanged
        ↓
        ListView rebuilds with new parameters
    }

Flow:
    User selects "lightgbm"
        ↓
    SelectedAlgorithm = "lightgbm"
        ↓
    LoadAlgorithmParameters()
        ↓
    Parameters.Clear() → ListView empties
        ↓
    Parameters.Add(...) → ListView shows "NumberOfLeaves"
        ↓

SCENARIO 5: COMMAND PARAMETER BINDING
--------------------------------------

Pass runtime data to commands:

XAML:
    <ListView ItemsSource="{Binding Items}"
              SelectedItem="{Binding SelectedItem}">
        <ListView.ItemTemplate>
            <DataTemplate>
                <StackPanel>
                    <TextBlock Text="{Binding Name}"/>

    public ICommand DeleteCommand { get; private set; }

    DeleteCommand = new RelayCommand(
        execute: item => DeleteItem((DataItem)item),
        canExecute: item => item != null
    );

    private void DeleteItem(DataItem item)
    {
        Items.Remove(item);
        ↓

        ↓
        ListView removes row
    }

        ↓

KEY TAKEAWAYS:

1. BINDING IS AUTOMATIC
   - No manual UI update code needed
   - PropertyChanged makes it happen

2. DATACONTEXT IS KING
   - All bindings look at DataContext
   - Hierarchical structure flows down

3. OBSERVABLECOLLECTION FOR LISTS
   - List<T> won't update UI
   - ObservableCollection<T> does

4. COMMANDS DECOUPLE UI FROM LOGIC
   - Button knows nothing about business logic
   - ViewModel handles everything

5. TWO-WAY BINDING FLOWS BOTH WAYS
   - User input → ViewModel
   - Code changes → UI

6. COMPUTED PROPERTIES REDUCE DUPLICATION
   - One property depends on others
   - Notify both when base changes

This is the MAGIC of MVVM!
Everything updates automatically through bindings.
